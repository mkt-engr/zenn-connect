# はじめに

- 記事の目的と背景
- エラーとローディングの範囲を限定することが重要な理由
- テストとコンポーネントカタログ（Storybook）を意識するメリット
  - Storybook を使うことでヘッダー、コンテンツ、フッターを並列して実装できる
- 記事のゴールと完成イメージ

# 完成形のコード構成

- 共通の構成パターン
- Header / Content / Footer に同じ構成を適用する方針

# アンチパターン：全体を 1 枚で包む境界

- 例: Header, Content, Footer をひとつの ErrorBoundary / Suspense にまとめる

## 問題点

- Footer が落ちただけで全体がエラーになる
- ローディングやエラーの影響範囲が広すぎる
- テストが複雑化する

# 望ましい構成：局所化された ErrorBoundary / Suspense（エラーとローディングの範囲を限定する）

- 各セクションを独立させる設計
- フォールバックをセクションごとに最適化
- 再試行の粒度を細かく制御できる
- ユーザー体験の向上とデバッグ容易性

# 最終的に作成される UI

# (不要かも)DummyJSON を使ったモック API

- DummyJSON の概要
- クエリパラメータで柔軟に検索できる特徴
- 利用するエンドポイント例
  - `/users/search`
  - `/carts/user`
  - `/products`

# Header コンポーネント

- 管理者のメールアドレスや画像の取得
- カート API の利用
- Storybook で見た目を確認する方法

# Content コンポーネント

- ユーザー一覧の取得と表示
- 検索ボックスと `useDeferredValue` の活用
- プロダクト一覧を表示する場合の例
- Storybook で状態バリエーションを確認

# Footer コンポーネント

- 重要度が低い情報（統計や件数など）の表示
- 落ちても全体に影響しない設計

# Vitest を使ったテスト戦略

- API モック方法（MSW または fetch のスタブ）
- 成功 / エラー / ローディングケースを局所化してテスト
- コンポーネント単位のテスト設計
- Storybook とテストの役割分担

# まとめ

- エラーとローディングを局所化する設計の利点
- テストとコンポーネントカタログを意識することで得られる開発体験
- 本番 API へ置き換える際にも活きる設計指針
